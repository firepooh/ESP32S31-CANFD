ESP32-S31 CAN-FD 버스 에러 시험

CAN1과 CAN2를 한 버스에 묶고 에러 상황을 하나씩 만들었다. 시나리오마다 재현 명령과 보드에서 관찰한 결과를 정리했다.

16개 시나리오 모두 예상대로 동작 에러 카운터, 상태 전이, 버스 오프 복구가 규격과 맞았다. 시험 중 찾은 펌웨어 문제 1건은 고쳤다.

에러 상태와 카운터 기준

결과를 읽을 때 쓰는 기준이다. 상태는 TEC와 REC 중 큰 값으로 정해지고, BUS_OFF는 TEC로만 들어간다.

ERROR_ACTIVE
WARNING
ERROR_PASSIVE
BUS_OFF
096128256 (TEC)

송신 에러는 TEC +8, 수신 에러는 REC +1(에러 플래그 뒤 우성이면 +8)이다. 성공하면 1씩 내려간다. ERROR_PASSIVE 상태의 송신 노드는 ACK 에러로 TEC가 오르지 않는다.

펌웨어에 넣은 에러 처리

시나리오를 만들고 결과를 보기 위해 추가한 기능이다. 코드는 main/canfd_port.c와 main/cmd_canfd.c에 있다.

에러 요약 로그

에러가 나는 동안 포트마다 500 ms에 한 줄을 출력한다. 종류별 증가분, tx_fail, 상태, TEC/REC가 들어간다. can_errlog off로 끈다.

상태 전이 로그

WARNING, PASSIVE, BUS_OFF로 바뀌면 경고로, ACTIVE로 돌아오면 정보 로그로 출력한다.

자동 버스 오프 복구

can_init <port> -a <ms>로 켠다. 버스 오프 뒤 지정 시간이 지나면 복구를 시작한다. 기본값은 0(수동)이다.

고장 주입

can_fault로 TX 핀을 우성이나 열성으로 고정한다. 고장 노드와 TX 단선을 흉내 낸다.

통계 확장

can_status에 err_passive, bus_off, recover 횟수와 주입한 고장을 표시한다.

송신 결과 보고 (수정)

can_send가 큐에 넣은 수, 실제로 보낸 수, 실패한 수를 출력한다. 버스 오프이면 복구 방법을 안내한다.

고장 주입 명령

TX 핀을 컨트롤러에서 떼어 GPIO로 고정한다. 닫힌 포트에도 걸 수 있고, can_init으로 포트를 다시 열면 풀린다.

명령핀 상태흉내 내는 고장
can_fault <port> dominantTX Low 고정노드가 버스를 우성으로 붙잡음
can_fault <port> recessiveTX High 고정TX 선 단선, 노드가 버스를 구동하지 못함
can_fault <port> off컨트롤러에 반환정상

시나리오별 재현 명령과 결과

시나리오는 실제 시험 순서대로 놓았다. 앞 시나리오의 상태를 이어받는 경우가 있으니 처음부터 따라 하려면 위에서부터 실행한다.

S01

상대 노드 없음 (ACK 에러)

ACK·재전송규격대로
재현 명령
can_init all
can_deinit 2
can_send 1 123 11223344
can_status 1
관찰 결과
ACTIVE→WARNING→PASSIVE
  • ACK 에러 12번 뒤 TEC 96으로 WARNING이 됐다.
  • TEC 128에서 PASSIVE가 됐고, 그 뒤로는 TEC가 128에 머물렀다.
  • 프레임은 초당 약 5300번 재전송됐다(재전송 한도 -1).
W CAN1 bus errors +12 (ack 12)  ERROR_WARNING TEC=96 REC=0
W CAN1 state: ERROR_ACTIVE -> ERROR_WARNING
W CAN1 bus errors +7 (ack 7)  ERROR_PASSIVE TEC=128 REC=0
W CAN1 state: ERROR_WARNING -> ERROR_PASSIVE
W CAN1 bus errors +2660 (ack 2660)  ERROR_PASSIVE TEC=128 REC=0
S02

상대 노드 복귀

복구규격대로
재현 명령 (S01에 이어서)
can_init 2
can_status 1
can_send 1 123 11223344 -n 40
관찰 결과
PASSIVE→WARNING→ACTIVE
  • CAN2가 켜지자 대기 프레임이 전달되고 TEC가 127로 내려갔다.
  • 정상 프레임 40개를 보내는 동안 TEC가 96 아래로 내려가 ACTIVE가 됐다.

state=ERROR_WARNING  TEC=127  REC=0

S03

재전송 한도 3회

ACK·재전송정상 동작
재현 명령
can_init 1 -r 3
can_deinit 2
can_send 1 123 11223344 -n 3
can_status 1
관찰 결과
ACTIVE→WARNING
  • 프레임마다 4번(최초 1번 + 재전송 3번) 시도한 뒤 버렸다.
  • ACK 에러 12번, tx_fail 3, TEC 96이었다.
  • 이때 can_send가 실패한 프레임도 "sent"로 보고했다. 이 문제는 고쳤다(S16).
W CAN1 bus errors +12 (ack 12)  tx_fail +3  ERROR_WARNING TEC=96 REC=0
tx_ok=0  tx_fail=3  rx=0  rx_drop=0
S04

단발 송신 (재전송 없음)

ACK·재전송정상 동작
재현 명령
can_init 1 -r 0
can_deinit 2
can_send 1 123 11223344 -n 2
관찰 결과
  • 프레임마다 ACK 에러 1번 뒤 바로 버렸다.
  • TEC는 프레임당 8씩 올라 16이 됐다.
CAN1: queued 2, sent 0, failed 2  (ERROR_ACTIVE TEC=16 REC=0)
S05

상대 노드가 listen-only

ACK·재전송규격대로
재현 명령
can_init 2 -m listen
can_init 1 -r 0
can_dump 2 on
can_send 1 123 11223344
can_status
관찰 결과
  • listen-only 노드는 ACK를 주지 않아 CAN1에 ACK 에러가 났다.
  • CAN2는 CAN1의 에러 플래그를 form 에러로 감지했다.
  • 무효가 된 프레임이라 CAN2는 받지 않았다(rx=0, dump 출력 없음).
CAN1  state=ERROR_ACTIVE  TEC=8  REC=0   tx_fail=1  ack=1
CAN2  state=ERROR_ACTIVE  TEC=0  REC=0   rx=0  form=1
S06

공칭 비트레이트 불일치 (500k와 250k)

비트레이트예상대로
재현 명령
can_init 1
can_init 2 -b 250000 -d 1000000
can_send 1 123 11223344
관찰 결과
CAN1, CAN2:ACTIVE→WARNING→PASSIVE
  • CAN1은 stuff 에러, CAN2는 form/stuff 에러를 냈다.
  • 두 노드 모두 REC가 511까지 올라 PASSIVE가 됐다.
  • 그 뒤 CAN1은 ACK 에러로 재전송을 계속했고, 버스 오프는 나지 않았다.

W CAN2 bus errors +96 (form 96)  ERROR_WARNING TEC=0 REC=96
W CAN2 state: ERROR_WARNING -> ERROR_PASSIVE
W CAN1 bus errors +2660 (ack 2660)  ERROR_PASSIVE TEC=16 REC=511
W CAN2 bus errors +2659 (form 1330 stuff 1329)  ERROR_PASSIVE TEC=0 REC=511

비트레이트 불일치 해소

S08

데이터 비트레이트 불일치 (2M와 1M)

비트레이트예상대로
재현 명령
can_init 1 -r 0
can_init 2 -d 1000000
can_send 1 100 -b -l 64 -n 5
can_status
can_test -D 12 -n 200 --nobrs
관찰 결과
  • BRS 프레임 5개가 모두 실패했다.
  • CAN1은 bit 에러(TEC 40), CAN2는 데이터 구간 stuff 에러(REC 45)를 냈다.
  • 공칭 속도만 쓰는 BRS 없는 FD 프레임 200개는 PASS였다.
CAN1  TEC=40  REC=0   tx_fail=5  bit=5
CAN2  TEC=0   REC=45  rx=0      stuff=5
--- CAN1 -> CAN2 : FD, 64 bytes, 200 frames ---  Result : PASS
S09

TDC 설정 없이 데이터 5/8 Mbps

비트레이트재현 불가
재현 명령
can_init all -b 1000000 -d 5000000 -r 0
can_test -D 12 -n 200 -t 2000
can_init all -b 1000000 -d 8000000 -r 0
can_test -D 12 -n 200 -t 2000
관찰 결과
  • 5 Mbps(6629 frames/s)와 8 Mbps(9268 frames/s) 모두 PASS였다.
  • SSP 레지스터의 리셋 기본값이 "측정한 송신 지연 + 10클럭"이라 TDC가 이미 켜져 있었다.
  • 드라이버에는 TDC를 끄는 경로가 없어 "TDC 없음" 실패는 만들 수 없었다.
trv_delay_ssp_cfg: ssp_src = 0 (measured delay + offset), ssp_offset = 10
S10

버스 우성 고착 (유휴 중)

고착·버스 오프트랜시버 보호
재현 명령
can_init all
can_fault 2 dominant
can_send 1 123 11223344
can_status
can_fault 2 off
관찰 결과
CAN1, CAN2:ACTIVE→WARNING→PASSIVE
  • 처음 수 ms 동안 버스가 우성이 되어 두 노드의 REC가 올랐다.
  • 그 뒤 트랜시버의 TXD 우성 타임아웃이 송신부를 꺼서 버스가 풀렸다.
  • CAN2는 ACK를 줄 수 없게 됐다. CAN1은 ack 에러, CAN2는 bit 에러를 냈다.
  • 고장을 풀자 대기 프레임이 전달됐다(tx_ok=1).

W CAN1 bus errors +1 (stuff 1)  ERROR_PASSIVE TEC=0 REC=145

S11

송신 중 버스 우성 → 버스 오프

고착·버스 오프규격대로
재현 명령
can_deinit 2
can_errlog off
can_send 1 123 11223344   # ACK 에러로 재전송 중
can_fault 2 dominant      # 닫힌 CAN2 핀으로 우성 주입

관찰 결과
PASSIVE→BUS_OFF
  • 송신 중인 CAN1이 bit 에러를 감지했다.
  • 우성이 이어지는 동안 TEC가 8씩 올라 256에서 BUS_OFF가 됐다.
  • 송신 중이던 프레임은 실패로 돌아왔다(tx_fail 1).

S12

버스 오프 중 송신과 수동 복구

복구정상 동작
재현 명령 (S11에 이어서)
can_send 1 123 11223344
can_recover 1
can_fault 2 off
can_init 2
can_test -n 200
관찰 결과
BUS_OFF→ACTIVE
  • 버스 오프 중 송신은 ESP_ERR_INVALID_STATE로 거부됐다.
  • can_recover 직후 ACTIVE가 됐고 TEC와 REC가 0으로 초기화됐다.
  • CAN2를 다시 연 뒤 양방향 200개가 PASS였다.

CAN1 send #1 failed: ESP_ERR_INVALID_STATE
I CAN1 state: BUS_OFF -> ERROR_ACTIVE
CAN1 recover: done

S13

TX 선 단선과 자동 복구

고착·버스 오프정상 동작
재현 명령

관찰 결과
ACTIVE→WARNING→PASSIVE→BUS_OFF→ACTIVE× 3

S16

버스 오프 안내 (수정한 can_send)

복구수정 확인
재현 명령
can_init 1
can_fault 1 recessive
can_send 1 123 11223344
can_fault 1 off
can_recover 1
관찰 결과
  • 실제로 보낸 수와 실패한 수, 현재 상태를 출력했다.
  • 버스 오프 상태라서 복구 방법을 함께 안내했다.
CAN1: queued 1, sent 0, failed 1  (BUS_OFF TEC=256 REC=0)
      CAN1 is bus-off: run 'can_recover 1' or enable auto recovery (can_init 1 -a <ms>)

시험에서 확인한 점

  • 트랜시버의 TXD 우성 타임아웃 때문에 노드 쪽 고장으로는 버스를 계속 우성으로 묶을 수 없다.
  • 송신 노드의 버스 오프는 노드가 송신하는 중에 우성을 걸거나, TX 선을 끊어서 재현했다.
  • REC는 수신에 성공해야만 내려간다. 송신만 하는 노드는 REC 때문에 PASSIVE에 오래 머물 수 있다.
  • 공칭 속도가 달라도 버스 오프까지는 가지 않았다. 두 노드 모두 PASSIVE에서 머물렀다.
  • TDC는 리셋 기본값으로 켜져 있다. --dssp는 보조 샘플 포인트 위치를 직접 정할 때만 쓴다.
  • 재전송 한도 -1에서는 ACK가 없는 프레임이 계속 재전송된다. can_init으로 포트를 다시 열어야 비워진다.

시험하지 못한 항목

CANH-CANL 단락, CANH-GND 단락, 종단 저항 제거처럼 버스 자체에 생기는 고장은 펌웨어로 만들 수 없다. 배선을 바꾼 뒤 같은 명령(can_status, can_send, can_test)으로 이어서 시험한다.

ESP32-S31 CAN-FD 2포트 테스트 펌웨어 · 시험 로그는 uart MCP(COM23)로 받은 콘솔 출력에서 발췌했다. 로그의 타임스탬프와 태그(canfd_port:)는 줄였다.
